## Verdict

**Theirs wins, by a wide margin.** Theirs is a complete attorney-facing product — contract ingestion (DOCX/PDF/OCR/paste), Claude extraction with quote verification, key dates with confirm/correct cascade, business-day/holiday deadline counting, per-method notice send-by dates, Q&A, notice drafting, persistence with history and actors — and every piece I could execute verified correct, including a Veterans-Day-aware business-day count my own manual count got wrong. Ours is a solid 311-line deterministic register core with exports theirs lacks (CSV/ICS/diff/party-exposure), but it ships **2 must-fix correctness bugs in the exact logic it exists for** (recurrence boundary, future-dated satisfaction records), and its end-to-end workflow is an order of magnitude behind: no ingestion, no satisfaction UI, prompt spec with no runnable harness.

## Must fix (ours) — 2

1. **Satisfaction on exactly a cycle due date discharges the wrong cycle and flags the paid cycle as missed.** `core/core.js:86-87` (`buildRegister`). Evidence (executed): obligations `Q` quarterly anchor `2026-03-31`, asOf `2026-11-08`, one record `satisfiedOn: '2026-06-30'` (paid on the 06-30 due date) → status `overdue`, flag `"breach risk: 2 missed quarterly cycles — due 2026-03-31, 2026-06-30"`. The 06-30 payment should discharge the 06-30 cycle; instead the code treats it as covering the *next* (09-30) cycle (`record.satisfiedOn >= past[len-2]`), leaving the cycle it actually paid counted as missed. Impact: paying on the due date — the single most common real-world case — produces a false breach-risk flag on the paid cycle; a false positive in the artifact's flagship output. Spec (`spec.md`, "Recurrence semantics") says the record covers the most recent past cycle "when it falls in that cycle's window"; the 06-30 window boundary belongs to the 06-30 cycle, not 09-30's window `(06-30, 09-30]` — the `>=` contradicts the spec, and no code path maps a record to the cycle whose window contains it. No test pins this boundary (core.test.js covers only mid-window records). Fix direction: map the record to the cycle whose window contains `satisfiedOn` (boundary date → that cycle, on time), and pin the boundary in tests.

2. **Future-dated satisfaction records are accepted and silently flip overdue to satisfied.** `core/core.js:60-64` (record selection) + branches at 86-96, 111-116. Evidence (executed): (a) recurring: record `satisfiedOn: '2027-12-31'`, asOf `2026-11-08` → flag `"satisfied 457 days late for cycle due 2026-09-30"` — lateness computed across a date 14 months after the register's as-of; (b) plain: due `2026-10-30`, record `2027-01-01`, asOf `2026-11-08` → status `satisfied`. Impact: a one-digit year typo (2026→2027) converts breach risk into compliance with no flag — precisely the failure the "deterministic, auditable register" positioning promises to prevent; the register is no longer a function of records known as of `asOf`. Fix direction: records with `satisfiedOn > asOf` should be excluded or flagged as future-dated/unverified, and lateness never computed across asOf.

## Worth considering (ours) — 4

3. **CSV formula injection.** `core/core.js:185-186`: `toCSV` quotes/escapes commas and quotes but not leading `=`, `+`, `-`, `@`. Verified: `party: '=HYPERLINK("http://evil","click")'` passes through verbatim. `party`/`sourceQuote` come from LLM extraction of counterparty contracts — untrusted text landing in a spreadsheet. Prefix dangerous leading chars with `'`.
4. **`renderRegister` breaks on `|` in flags/text.** `core/core.js` `renderRegister` builds Markdown table rows without escaping pipes; any flag or obligation text containing `|` corrupts the table.
5. **ICS lines not folded at 75 octets** (RFC 5545 §3.1). `toICS` emits arbitrarily long DESCRIPTION/SUMMARY lines (long `sourceQuote`, flags). Most clients tolerate; strict validators reject.
6. **`condition` silently dropped when `dueDate` is also set.** Spec says the fields are mutually exclusive "in practice"; code takes the dueDate branch with no flag, so a mis-filled extraction hides the event trigger entirely. A one-line "both set" flag would surface it.

## Recorded only

- Ours: demo offers no way to record a satisfaction except hand-editing JSON; no ingestion path at all — `spec.md`'s "extract them yourself or with the documented LLM prompt" is the weakest link vs theirs' shipped DOCX/PDF/OCR pipeline.
- Ours: verified spec claims that hold — ghost satisfaction ids ignored (`core.test.js:110`), latest-record-wins order-independent, month-end/leap clamps correct (`Jan31+1mo→02-28`, `Feb29+1y→02-28`).
- Theirs: no CSV, no iCalendar, no register diff, no per-party exposure rollup — ours' real, verifiable differentiators.
- Theirs: a contract must fit one Claude call (≤256 KiB prompt budget, `CONFIG.read.maxPromptBytes`); longer contracts dead-end at "too long" with split-it-up advice. OCR capped at 60 pages.
- Theirs: roll rule deliberately "never later" for before-event deadlines (a Saturday 30-days-before date rolls *back* to Friday, not forward to Monday per a literal §11 reading) — documented conservative choice in comments; errs safe for the client.
- Theirs: served over plain HTTP outside the Claude host it renders the full sample with dates regenerated relative to today, correct copy/read-only states, zero console errors.
